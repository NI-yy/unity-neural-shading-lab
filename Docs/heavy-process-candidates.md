# 高負荷処理の探索（2026-11-07）

## 見つかった候補

**第一候補は、方向光の遮蔽を求めるためのカスケード影マップ生成。材質計算には限定しない。** 新たな固定視点 `shadow-stress` では `Draw Main Light Shadowmap` が3回とも中央値約1.26 msで、全体2.27〜2.30 msの約55%を占めた。影をハードにしても生成コストは残り、影自体を無効にすると全体は0.90〜0.93 msになった。影のフィルタ関数だけを置き換えても、この1.26 msは消えない。大きい処理を置き換えるには、影マップを毎フレーム描く代わりに遮蔽・可視率を求める方式が必要。

**第二候補はSSAOの出力と、そのための法線生成。** 元の視点ではAO本体は約0.05 msだが、SSAOを外すと約0.33 msの深度・法線プリパスが約0.17 msの深度のみのプリパスに変わり、全体で0.18〜0.25 ms下がった。AO本体だけをニューラル化して法線生成を残す構成は、高速化の余地が小さい。

ここまでで重い処理と発生条件は見つかった。**ニューラル方式が通常の方法より有利かは未検証。** 影の候補は、まず静的な建造物の方向光遮蔽を対象に、世界位置・光方向・シーン表現から可視率を近似する設計が考えられる。これは提案であって実装結果ではない。動く植生や水車の遮蔽は、静的な世界位置と光方向だけでは決まらない。従来の動的影を残す構成、または動的状態を入力に含める必要がある。採用判断では、削減できる影生成時間から、残す動的影・推論・追加バッファのコストを差し引く。影のキャッシュ、ベイク、距離・カスケード調整等との比較も必要。静的・動的オブジェクト別の影生成コストはまだ分離していない。

SSAOは深度からの法線再構成という通常の対照手段を先に比較する。URPには `Source=Depth` がある。今回のビルドはDepthNormals用のシェーダバリアントを使用しており、Depth用バリアントの保持を確認せず実行時だけ設定を切り替える比較はしていない。約0.2 msという小さい予算の中に推論・入出力・履歴処理を収める必要があるため、影遮蔽より優先度を下げる。ニューラルモデルの実装・学習は行っていない。

## 確認測定

同じUnity 6000.3.12f1 / URP 17.3.0 / RTX 4070 SUPER / DX12 / Windows x64 Mono Development Playerで、Editorに接続せずGPU Usageのbinary logをPlayer自身に保存した。[Issue #3](issue-3-dx12-independent.md)で独立計測と照合した手法を再利用している。以下はこの計測付きDevelopment Playerでの比較で、ReleaseやProfilerなしの絶対時間へ外挿しない。

Desktop品質、1920×1080、Render Scale 1、動的解像度・STP・TAA・VSync・FPS上限なし、影マップ8192・4カスケードを共通とした。元のDemoシーンとカメラ設定は保存し直していない。診断用の差は明示的な `-candidate` 引数でPlayerのメモリ内だけに適用する。`-candidate` がなければ診断変更は適用しない。

各条件は初期化10、ウォームアップ300、1000フレーム、遅延排出8フレーム、別プロセスで3回。5条件を1回ずつ測るラウンドを3回行い、2ラウンド目は条件順を反転した。終了時クラッシュしたSSAO除去の1試行は保全して採用せず、同条件を再取得した。採用した15回は全てPlayer終了コード2（FrameTimingManagerの欠測）で、**GPU Usageの `PlayerLoop` は各回1000/1000取得、欠測0**。

|---|---|---|---|---|
| 初期 | Reference | 1.636 / 1.608 / 1.610 | 1.933 / 1.894 / 1.902 | 深度・法線 0.330 / 0.327 / 0.328、SSAO 0.048 / 0.050 / 0.051 |
| 初期 | SSAO除去 | 1.391 / 1.410 / 1.4305 | 1.688 / 1.709 / 1.735 | 深度のみ 0.168 / 0.166 / 0.168 |
| shadow-stress | Reference | 2.288 / 2.295 / 2.266 | 2.594 / 2.614 / 2.581 | 影生成 1.259 / 1.261 / 1.260 |
| shadow-stress | ハードシャドウ | 2.199 / 2.202 / 2.222 | 2.514 / 2.515 / 2.529 | 影生成 1.229 / 1.2605 / 1.265 |

無効化は原因を切り分けるための対照であり、画質を維持した改善として採用していない。SSAO除去では接触部の陰影、影無効では建物・水車・岩の影が変わる。影無効による全体差1.332〜1.393 msは、影生成に加えて受光側の影参照等も除いた差であり、全てを一つのシェーダ関数のコストとは扱わない。親子のGPUマーカーも重複加算しない。

### 固定した追加視点

`shadow-stress` は水車付近を映す探索視点を、列挙順に依存しない値として固定したもの。

- position: `(-129.9334717, 12.7908611, 409.6483459)`
- rotation quaternion: `(0.0644175485, -0.3694965839, 0.0256864037, 0.9266406298)`
- field of view: `50°`
- 光源は元のシーンのまま。カメラ以外のシーン資産は変更していない。

この視点で影生成が初期視点の約0.31〜0.32 msから増えた。カメラとカスケードの可視範囲に依存した結果であり、全視点で1.26 msになるとは主張しない。各カスケードの寄与、ジオメトリ処理とラスタライズの内訳は未分離。

## 材質以外も含めた探索

既存のPlayer単独3回×1000フレームから全GPU階層も抽出した。[階層集計](../Benchmarks/Candidates/baseline-hierarchy-summary.csv)では、初期視点は不透明描画約0.58 ms、深度・法線約0.33 ms、影生成約0.32 msが中心。フォグ2段の同名フルスクリーンパスは合計約0.063 ms、Bloom約0.056〜0.057 ms、SSAO約0.050〜0.051 ms、透明描画約0.041 msだった。フォグ・Bloom・透明描画を現時点の第一候補にはしない。

[探索用の単回測定](../Benchmarks/Candidates/screening-player-only/summary.csv)では、フォグ除去、ポスト処理除去、低品質・ハードシャドウ、別カメラ／光源も確認した。これらの単回の全体差を確定した高速化とは扱わない。不透明描画には材質評価、照明、影参照、ジオメトリ、ラスタライズが混在する。初期視点の不透明描画約0.58 ms全体を「ニューラルで置き換えられる計算」とは数えない。

水面を探すため最大のWaterLakeメッシュ全体を収めた `lake` 視点は、実際の不透明・透明描画マーカーが出ず、有用な水面比較としては棄却した。探索時の `waterfall` 視点も、透明描画は約0.039 msで、増えていたのは影生成だった。滝のシェーダが重いという結論にはしていない。植生除去の試行はPlayerがクラッシュしたため採用していない。レンダラー一覧はフラスタムとの交差候補で、実際のLOD選択・遮蔽後の描画数や寄与率ではない。

## データと欠測

- [確認測定の集計](../Benchmarks/Candidates/confirmed-player-only/summary.csv) と各 `run-*` の `frames.csv`、`candidate-info.json`、`matched-frames.csv`、GPUの全フレーム書き出しを保存した。生の `.raw` はGit対象外の `LocalData/Candidates/confirmed-player-only/`。
- FrameTimingManagerのGPU時間0は各回9〜107件あり、元CSVにそのまま残した。補間やProfiler系列との穴埋めをしていない。性能比較の主系列は欠測のないPlayer側GPU Usage。意図的に外したSSAO・影等のマーカーが存在しない場合も、GPU時間0を作って埋めていない。
- 統計は各回を分けて計算し、中央値・p95は正の有限なGPU時間を昇順に並べた位置 `(n-1)p` の線形補間。有効件数と欠測件数は系列ごとに保存する。
- FTMとProfilerのフレーム開始QPCを一意に対応させた。全15回で1000フレームずつ重複なし。最大差0.019701 ms、最大でも隣接Profilerフレーム間隔の0.642%以下だった。元の固定0.01 ms閾値では7フレームが外れたため、曖昧でないことを全件確認し、「差0.05 ms以下、かつ隣接間隔の1%以下、かつ対応の重複なし」を使用した。これは時刻の対応づけで、GPU時間の補間ではない。
- このセッションのPresentMonは既存ETWセッションとの競合、その後は対象CSVなし・イベント損失となった。PIDを指定した試行もCSVを取得できなかった。独立計測結果として使っていない。`source-state.json` の `independentTiming=false` を明記した。失敗試行とクラッシュは [attempts.md](../Benchmarks/Candidates/attempts.md) に区別して記録した。

## 再現と次の判断

1. 同じ既存プロジェクトで、`Tools/Run-Baseline.ps1 -Build -BuildOnly -Development`。サンプル資産は既存のものを使う。
2. `Tools/Run-Candidates.ps1 -Phase <新規名> -UnityOnly -NoExport -Cases <視点/条件> -RunIndex <1..3>` で測る。今回の5条件は `initial/reference`、`initial/no-ssao`、`shadow-stress/reference`、`shadow-stress/hard-shadows`、`shadow-stress/no-shadows`。ラウンドごとに条件を交代し、既存の出力を上書きしない。失敗回は別保存してから再取得する。
3. 全3回取得後、同じ5条件を `-Cases` に渡し `-ExportOnly -Repeats 3` でCSV化する。`python Tools/Summarize-Candidates.py --phase <新規名>` で集計・QPC対応・件数・取得状態を検証する。GPU時間0を有効値へ変換しない。
4. 同じ条件を `-CaptureOnly` で別起動する。CaptureOnlyの終了時クラッシュが残るため、画像の生成・寸法・ハッシュと終了コードを別々に記録する。

次に比較する処理を一つ選ぶなら**影の可視率近似**を優先する。1.26 msの影マップを生成し続け、その結果を入力に取るだけのモデルには大きい高速化予算がない。まず静的・動的な影生成を分離し、通常のキャッシュ／ベイク／距離調整と比較した上で、影マップを省ける範囲と画質・照明条件を定義する。SSAOは法線を深度から再構成する通常方式との比較を先行させる。ここまでの診断ではネットワークの推論時間・画質・学習可能性は検証していない。
